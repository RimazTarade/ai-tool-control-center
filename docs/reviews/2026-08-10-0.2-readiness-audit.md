## Current 0.1 capabilities

### Implemented and protected

- Tauri 2 desktop shell with a local React interface.
- SQLite-backed pending discovery queue and reviewed inventory.
- Explicit import, ignore-once, and keep-unknown review decisions.
- Separate installation, registration, enablement, runtime, connection, authentication, health, confidence, and review fields in the discovery model.
- Quick filesystem scan executed outside the UI thread with a cancellation token.
- Bounded scan event channel between the Rust scanner and desktop shell.
- Basic high-noise directory exclusions and `follow_links(false)` traversal.
- Incremental scan events and persistence of discoveries before frontend notification.
- Versioned Python scanner protocol foundation.
- Public-source and private-path repository policy checks.
- Windows-hosted CI running Rust, Python, frontend, repository policy, and Tauri release compilation.

### Partially implemented

- Review queue: import, ignore-once, and keep-unknown are present, but the complete planned edit/import, merge, always-ignore, pagination, revision-token, and bulk-safe workflow is not.
- Scan orchestration: one filesystem quick scanner and one active-scan registry exist, not the planned multi-scanner coordinator with independent deadlines, pause/resume, scanner isolation, and coalesced progress.
- Python scanner: protocol and generic parsing foundations exist, but bundled-runtime acquisition, absolute-path supervision, Windows process-tree cleanup, and broad Claude/Codex/Docker interpretation are not yet present.
- Frontend: Overview, Inventory, Review Queue, scan progress, and cancellation are functional foundations. Other navigation destinations remain placeholders.

## Missing 0.2 capabilities

### Milestone 4: native Windows discovery

Current Rust scanning is filename-signal filesystem traversal over supplied roots. There is no dedicated native Windows discovery module yet.

Required work:

1. Windows known-location resolution without personal hard-coded paths.
2. PATH executable observation and deduplication.
3. Installed-application discovery from relevant HKCU/HKLM uninstall registry views.
4. Process observation with partial/access-denied handling.
5. Windows service observation and state mapping.
6. Listening TCP endpoint observation with optional process association.
7. Bounded launcher and shortcut metadata observation in approved roots.
8. Native errors converted into per-scanner partial failures rather than panics.
9. Reparse/junction safety and traversal regression tests.
10. Evidence/fingerprint generation that feeds the existing `Discovery` model and mandatory review queue.

### Milestone 5: bundled Python scanner engine

Required work:

1. Harden protocol validation and malformed/oversized input handling.
2. Expand product-specific interpretation for Claude, Codex, common MCP configuration, and Docker/CLI output where appropriate.
3. Add an official CPython 3.14 x86-64 runtime manifest with immutable download metadata and SHA-256 verification.
4. Add deterministic runtime staging outside source control.
5. Add a Rust supervisor that launches the absolute application-owned interpreter rather than ambient system Python.
6. Bound stdin, stdout, and stderr; redact errors before persistence/IPC.
7. Add timeout and cancellation handling with owned process-tree cleanup on Windows.
8. Add a staged-runtime smoke test that neutralizes common system-Python fallback variables.

### Minimum scan-orchestration seam required by 0.2

- stable scanner IDs;
- bounded concurrent execution;
- one cancellation root with per-scanner cancellation/deadlines;
- independent scanner failure events;
- incremental discoveries;
- UI navigation remaining responsive during a deliberately slow scanner;
- terminal scan state only after all selected scanners complete, fail, or cancel.

Full deep-scan UX and later health/dependency features remain deferred.

## Direct blockers discovered

1. `engine/rust/control-center-core/src/windows.rs` described by the approved implementation plan does not exist.
2. `scan.rs` is currently both filesystem implementation and scan event contract; it needs a coordinator boundary before additional scanners are added.
3. `apps/desktop/src-tauri/src/lib.rs` still owns command, state, persistence, and scan-event wiring in one file. Split only when the multi-scanner seam requires it.
4. CI runs on pull requests and `main` pushes. A draft pull request will be useful once the first test-first commit is pushed so Windows CI can serve as the authoritative hosted Windows runner.
5. Final real-machine acceptance still requires the local Windows checkout because hosted runners cannot validate the user's actual Registry, services/processes, installed Claude/Codex configuration, or interactive Tauri behavior.

## Deliberately deferred

- complete review merge/edit/bulk workflow unless a required seam forces it;
- full health workspace;
- dependency visualization;
- backup/restore;
- declarative community adapter workflows;
- safe operational action execution;
- final NSIS/portable distribution;
- signing, SBOM, and release publication automation.

## Execution order

1. Add the native Windows discovery seam test-first.
2. Implement safe Windows path identity and PATH discovery.
3. Implement uninstall-registry observation.
4. Implement process, service, and TCP observations.
5. Add bounded launcher/shortcut observation where supported by the plan.
6. Upgrade scan coordination for independent scanner failures, timeouts, cancellation, and incremental events.
7. Harden and extend the Python scanner protocol/interpreters.
8. Add verified bundled CPython staging and Rust supervision.
9. Extend frontend scan-state/error integration and protect navigation during a slow scan.
10. Run repository policy, Rust, Python, frontend, Tauri, and Windows CI gates.
11. Perform local Windows acceptance only after hosted CI is green.
12. Update version-facing documentation to 0.2 only after all 0.2 acceptance gates have evidence.

## First implementation slice

The first test-driven slice is Windows path identity and deduplication, which PATH discovery needs. The test is intentionally committed before production code so the missing seam is observed failing before implementation.
